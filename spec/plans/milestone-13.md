### בקשות מוצרים (כללים, ו-Gemini רק לשיקול דעת)
1. **בקוד:** שם שכבר קיים בקטלוג (`products.json`, השוואה אחרי ניקוי רווחים וסימנים): לדחות, "כבר בקטלוג".
2. **ב-Gemini, קריאה אחת לכל הבקשות של היום:** לכל בקשה, האם היא ספאם או טקסט פוגעני, והאם היא אותו מוצר כמו בקשה מאושרת או ממתינה אחרת. Gemini מקבל רק את שמות הבקשות ואת שמות הבקשות הקיימות. בלי זהות של משתמשים.
3. **המלצות:** ספאם או פוגעני: לדחות. כפולה: לאחד לבקשה X. אחרת: לאשר.
4. **חשיבות:** מספר הקולות, ומספר הבקשות שאוחדו לתוכה.
5. Gemini לא זמין או החזיר שגיאה: הבקשות נשארות "לא נבדקו", והדוח אומר זאת. אף בקשה לא נדחית בגלל תקלה.

### איחוד בקשות (קולות מתחברים)
- סטטוס חדש לבקשה: `merged` (אוחדה).
- יוני כותב בעורך `merged` בבקשה שהסוכן סימן כפולה. טריגר מעביר את הקולות שלה לבקשה שאליה אוחדה (`duplicate_of`). מי שכבר הצביע על שתיהן נשאר עם קול אחד, והקול השני חוזר אליו.
- בלי `duplicate_of`: הטריגר לא מאפשר `merged`, כדי שלא יאבדו קולות.

### מה הסוכן לא עושה
- לא משנה סטטוס. רק כותב המלצה, נימוק, חשיבות ו"כפול של". יוני מאשר או דוחה, כמו היום.

## חלק ב: דוח הבוקר

### טבלה חדשה `agent_events`
| עמודה | סוג | הערה |
|---|---|---|
| `id` | bigint | |
| `agent` | text | `community`, `promos`, `product_match`, `catalog` |
| `kind` | text | `action` (מחכה ליוני) או `info` (לידיעה) |
| `title` | text | שורה אחת בעברית |
| `ref_table`, `ref_id` | text, bigint | השורה שהאירוע מדבר עליה, אם יש |
| `created_at` | timestamptz | |
| `reported_at` | timestamptz | מתי נכלל לראשונה בדוח |
| `handled_at` | timestamptz | מתי טופל |

- **טופל:** אירוע `info` נחשב מטופל אחרי שנשלח בדוח פעם אחת. אירוע `action` נשאר פתוח עד שיוני מחליט. בקהילה זה אוטומטי: כשסטטוס הדיווח או הבקשה יוצא מ-`pending`, טריגר מסמן את האירוע כמטופל.
- **הרשאות:** אין גישה מהדפדפן בכלל. רק n8n, עם ה-Credential של Supabase.
